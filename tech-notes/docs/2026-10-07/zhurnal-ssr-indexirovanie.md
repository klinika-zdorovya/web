# Журнал работ: индексация сайта (SSR/SSG), 07.10.2026

Рабочий журнал для клиентского отчёта (шаблон: `tech-notes/templates/report/`). Пишется по ходу работ, записи не переписываются задним числом. Все пункты «Проверено» подтверждены запуском, а не предположением. Исполнитель: Роман Пальмин (с Claude Code). Ветка: `KZ-XX_ssr-experiment` (от `dev`, в `main` не вливалась, деплой не затронут).

## Исходная проблема

Страницы сайта `klinika-zdorovya.spb.ru` открываются у людей, но **не индексируются поисковиками**.

## 1. Что видит поисковый робот на проде (проверено)

Проверка `https://klinika-zdorovya.spb.ru/publications/konstitutsionalnaya-morfologiya`, только чтение (curl):

- Ответ 200, файл 3079 байт: пустой контейнер `<div id="__nuxt"></div>`. **Нет `<title>`, нет `<h1>`, нет текста.** Страница наполняется только после выполнения JavaScript в браузере.
- Один и тот же файл отдаётся для любого адреса (со слэшем, без слэша, любой несуществующий).
- `robots.txt` и `sitemap.xml` отдают ту же пустую оболочку со статусом 200 (настоящих файлов на сайте нет).
- Сборка на проде датирована январём 2026 (`prerenderedAt`), настройка `ssr: false`.
- В публичной конфигурации `siteUrl` указывает на `https://klinika-zdorovya.ru`; см. п. 5.

**Вывод:** причина отсутствия индексации в том, что без выполнения JavaScript страница пустая и одинаковая у всех адресов.

## 2. Окружение и сборка (проверено)

- Проект собирается командой `generate` (статическая генерация), на хостинг заливается по FTP; хостинг статический, Node-сервера нет. Поэтому подходящий вариант: SSG с `ssr: true` (готовый HTML каждой страницы на этапе сборки), SSR «на лету» на их хостинге невозможен.
- Сборка идёт на **Node 20** (как в CI); на Node 24 падает нативный модуль `better-sqlite3`.
- Изменено: `ssr: false` → `ssr: true` в `nuxt.config.ts`.
- Результат: сгенерировано 96 маршрутов, в HTML каждой страницы реальный текст и заголовок.

## 3. Найденная ошибка при прямом заходе на страницу (воспроизведена)

- Симптом: при включённом `ssr: true` прямой заход на статью новости или публикацию после загрузки превращается в **404**, хотя HTML с сервера был корректным.
- Причина: адрес со слэшем (`/news/2025-01-01/`) не совпадал с путём контента (`/news/2025-01-01`) в запросе к Nuxt Content на клиенте. Без слэша страница открывалась, со слэшем нет. Обычный сервер для папки делает редирект именно на адрес со слэшем, поэтому посетитель и робот попадали на 404.
- Исправление: функция `normalizeContentPath` (`app/composable/contentPath.ts`) убирает завершающий слэш; применена в трёх страницах (`app/pages/[...slug].vue`, `news/[...slug].vue`, `publications/[...slug].vue`). В публикациях дополнительно отфильтрован пустой сегмент пути.
- Проверено: headless Chromium, 16 типов страниц (главная, клиника, направления, цены, контакты, вопросы, отзывы, пациентам, списки новостей и публикаций, статья новости, публикация), обе формы адреса. Везде корректный контент, ошибок в консоли нет, несуществующая страница даёт 404.

## 4. Проверка на настоящем Apache (проверено)

Файл `.htaccess` хостинга (в репозитории отсутствует, получен от Романа) содержит правило «любой адрес без файла и папки отдавать как `/index.html`». Проверено в контейнере Apache 2.4 с этим файлом:

- Адрес без слэша получает редирект на адрес со слэшем (то место, где падало до исправления кода).
- Любой несуществующий адрес (`/abc`, `/publications/oops`, `/_nuxt/missing.js`) отдаётся со статусом **200** вместо 404 («мягкие 404»; для поиска это мусорные страницы).
- Вариант `.htaccess` из одной строки `ErrorDocument 404 /404.html` (SPA-правило убрано): существующие страницы 200, несуществующие честные 404; все 16 типов страниц работают в обеих формах адреса.
- Не проверено, остаётся риском: перед Apache на проде стоит nginx-прокси (`openresty`); редирект Apache со слэшем за прокси иногда формирует адрес с `http://` или с лишним портом. Воспроизвести локально нельзя; после выкладки проверить `curl -I` на нескольких адресах, откат подготовить (предыдущая сборка).

## 5. Домен (найдено при проверке)

- `klinika-zdorovya.ru` и `klinika-zdorovya.spb.ru` указывают на разные серверы. На `.ru` открывается **другой сайт** («Медицинский центр в Казани», PHP), не клиника.
- В проекте `siteUrl` по умолчанию `https://klinika-zdorovya.ru`; на этот домен ссылаются структурированные данные (url, logo, email `info@klinika-zdorovya.ru`). То есть разметка клиники указывает на чужой домен.
- Решение: канонический адрес `https://klinika-zdorovya.spb.ru`. (Подтверждение у клиники по почте `info@…ru` и фактической принадлежности `.ru` не проводилось.)

## 6. Побочные находки (SEO), на момент записи не исправлены

- У большинства страниц одинаковый `<title>`; уникальный только у публикаций.
- Нет `canonical`, нет настоящих `robots.txt` и `sitemap.xml`.
- На страницах статей два `<h1>`: из шаблона (с неверным текстом «Все новости»/«Главная») и заголовок статьи.
- Ключ Яндекс.Карт лежит в открытом виде в `nuxt.config.ts`; ограничить по домену в кабинете Яндекса.

## 7. SEO-минимум в той же ветке (сделано и проверено сборкой)

- **Домен по умолчанию** `siteUrl`: `klinika-zdorovya.ru` заменён на `klinika-zdorovya.spb.ru` в `nuxt.config.ts` и `useStructuredData.js`. На CI переменной `NUXT_PUBLIC_SITE_URL` нет, поэтому на проде сработает это значение. В локальном файле `.env` у Романа (в git его нет) значение старое `.ru`; при локальной сборке его нужно заменить или переопределить.
- **`canonical` и `og:url`** на каждой странице: `https://klinika-zdorovya.spb.ru/<путь>/` (со слэшем, как отдаёт папки сервер). Раньше `og:url` был зашит на чужой домен `.ru`, `canonical` отсутствовал.
- **Уникальные `<title>`**: у новостей и страниц контента заголовок берётся из самой страницы; у разделов «Цены» и «Контакты» исправлен поиск названия (мешал слэш в конце адреса). Результат: из 71 страницы с общим заголовком осталось 17 (разделы без собственного заголовка в контенте и страницы-списки, см. п. 8); до правки счёт общих заголовков не велся, на проде он был общим у всех страниц, кроме публикаций.
- **`robots.txt`** (`public/robots.txt`): разрешено всё, указана карта сайта. Раньше по этому адресу отдавалась пустая оболочка со статусом 200.
- **`sitemap.xml`**: создаётся автоматически после сборки скриптом `scripts/generate-sitemap.mjs` по реально собранным страницам, 71 адрес; команда `generate` в `package.json` теперь вызывает его после `nuxt generate` (на CI команда та же `npm run generate`).
