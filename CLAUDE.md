# CLAUDE.md — Клиника здоровья (kz-web-2.0)

Инструкции для Claude Code в этом репозитории. Дополняет
`~/Projects/CLAUDE.md` (правила безопасности верхнего уровня — не удалять/не
трогать `legacy-docs/` без явного запроса).

## Что это за проект

Сайт клиники «Передовые технологии здоровья» — Nuxt 3 + Nuxt Content 3,
статическая генерация (SSG), контент хранится в git как Markdown/YAML/JSON.
Полное описание — `documentation/Chapter 1. Introduction/Introduction.md`.

**Стек:** Nuxt 3 (Vue 3, `ssr: false`, compatibilityVersion 4), Nuxt Content 3,
Tailwind CSS, `@nuxtjs/color-mode`, `better-sqlite3` (используется Content для
индексации). Пакетный менеджер — **pnpm**.

## Команды

```bash
pnpm install
pnpm dev        # http://localhost:3000
pnpm build
pnpm generate    # статическая генерация — то, что реально деплоится
pnpm preview
```

Нет настроенных lint/test скриптов в `package.json`, несмотря на упоминание
`pnpm lint` в документации — прежде чем полагаться на него, проверить
актуальный `package.json`.

## Структура (кратко)

- `app/` — код Nuxt: `components/`, `pages/`, `layouts/`, `composable/`, `plugins/`
- `content/` — **весь контент сайта** (Markdown/YAML/JSON): `clinic/`,
  `dimensions/`, `news/`, `publications/`, `reviews/`, `data/` (врачи, FAQ,
  прайс-лист, контакты, навигация)
- `public/images/` — статические изображения, сгруппированы по разделам
- `documentation/` — подробная документация проекта по главам (см. ниже)
- `legacy-docs/` — **вне git** (в `.gitignore`), старый код и не связанные с
  кодом документы старой версии сайта. Не коммитить, не трогать без запроса.
- `tech-notes/` — обсуждение и фиксация технических решений (хостинг, домен,
  инфраструктура, деплой) + хранение связанных документов (исследования,
  ответы внешних AI-инструментов и т.п.). В git, но без секретов/ключей —
  см. `tech-notes/README.md`. Журнал вопросов/решений — `tech-notes/DECISIONS.md`.

Полная карта дерева с комментариями —
`documentation/Chapter 2. Project structure/Scructure.md`.

## Документация проекта — где искать

`documentation/` уже написана подробно по главам, читай их вместо повторного
ресёрча:

1. Introduction — назначение, аудитория, стек
2. Project structure — структура репозитория, конфиги, частые проблемы
3. CMS Nuxt Content — форматы данных, front matter, запросы к контенту
4. Add and edit content — как добавлять новости/врачей/публикации
5. Workflow.Github — процесс редактирования через GitHub UI, конвенции коммитов
6. Deploy — разбор `.github/workflows/main.yml`, секреты, troubleshooting
7. Developers — расширение функциональности, новые разделы, компоненты
8. FAQ

Если меняешь структуру контента/деплоя — обнови соответствующую главу, а не
только код.

## Конвенции контента (см. также главу 4 и 5)

- Новости и отзывы: `content/news/YYYY-MM-DD.md`, `content/reviews/YYYY-MM-DD.md`
- Публикации: `content/publications/<транслит-темы>.md`
- Врачи: `content/data/doctors/<номер>.<фамилия>.json` — следующий номер
  смотреть по последнему существующему файлу
- Изображения — латиницей, без пробелов, JPG для фото / PNG для лого и
  прозрачных изображений

## Git-процесс

- Тикеты — Jira-подобные `KZ-<номер>` (`KZ-XX` — если тикета нет/технический
  коммит). Формат коммита в этом репо на практике: `KZ-41 SEO-оптимизация`
  (номер тикета + краткое описание), а не `Тип: описание` из главы 5 —
  ориентируйся на `git log`, а не только на документацию, если они разойдутся.
- Ветки называются по тикету, например `KZ-41_seo-optimisation`.
- **Деплой автоматический**: любой push в `main` запускает
  `.github/workflows/main.yml` → `pnpm generate` → FTP-заливка
  `.output/public/` на хостинг. Это необратимо влияет на прод-сайт — пушить в
  `main` только осознанно.
- Известная нестыковка: `paths-ignore` в workflow игнорирует `docs/**`, но
  реальная папка документации называется `documentation/**` — правки в
  `documentation/` сейчас всё равно триггерят полный деплой. Не чинить молча,
  спросить перед изменением workflow-файла.

## Самодокументирование

Ведём `DIARY.md` в корне проекта — короткий журнал рабочих сессий (что
сделано, какие решения приняты и почему). После заметной единицы работы
(фича, багфикс, решение по архитектуре/контенту) — добавляй запись. Не нужно
логировать тривиальные правки по мелочи.

## Клиентские отчёты

Все отчёты о выполненных работах, которые предъявляются заказчику (клинике),
делаются по единому шаблону в `tech-notes/templates/report/` — не собирать
дизайн отчёта заново. Инструкция и принципы оформления — в
`tech-notes/templates/report/README.md`; готовые примеры и сами отчёты —
в `tech-notes/docs/`.
